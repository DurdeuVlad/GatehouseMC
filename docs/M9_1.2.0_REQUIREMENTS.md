## 1. Milestone objective

GatehouseMC 1.2.0 must make the whitelist workflow behave as one coherent administrative system across Minecraft, Discord, and Telegram.

The release is accepted only when:

1. all textual administrative commands are under one canonical /gatehouse namespace;
2. Fabric, Forge, and NeoForge expose the same Minecraft command contract;
3. Discord and Telegram expose the same Gatehouse command vocabulary through their native command mechanisms;
4. every administrative surface calls the same loader-neutral command and decision services;
5. terminal decisions remain safely recoverable;
6. repeated player reconnects cannot spam the admission queue, database, outbox, Discord, or Telegram;
7. setup, status, errors, and degraded-state recovery are understandable without reading server logs for normal operational problems;
8. provider interactions are state-aware, authorized, replay-safe, and mobile-friendly;
9. reload cannot silently destroy a working runtime;
10. release-gate tests prove the above on all three supported loader targets.

This is a minor release because it adds a unified administrative command surface, guided provider setup, RBAC, abuse controls, provider command handling, and new operator UX. A smaller emergency recovery patch may be released separately as 1.1.1, but M9 itself targets 1.2.0.

## 2. Non-negotiable product decisions

### M9-D001 — /gatehouse is the only textual command root

The only public textual command namespace is:

~~~text
/gatehouse
~~~

This applies to:

- Minecraft chat;
- Minecraft console;
- RCON;
- Discord application commands;
- Telegram bot commands.

The following roots MUST NOT be registered or documented in 1.2.0:

~~~text
/gh
/wlreq
/approve
/deny
/block
/undo
/reopen
/status
/requests
/setup
~~~

The old Minecraft aliases /gh and /wlreq are intentionally removed in 1.2.0. Do not preserve them as deprecated aliases. Do not add another convenience root.

Buttons and menus may invoke Gatehouse actions internally, but they are not separate textual commands.

### M9-D002 — One command model, three adapters

Minecraft, Discord, and Telegram MUST NOT implement independent business command semantics.

Introduce loader/provider-neutral application services with these responsibilities:

- AdminCommandService: executes administrator operations and returns structured results;
- RequestResolver: resolves request references and usernames according to Section 7;
- AdminAuthorizationService: resolves VIEW, DECIDE, and MANAGE capabilities;
- GatehouseStatusService: produces one structured status model for all UIs;
- RequestActionPolicy: determines which actions are valid for a request state;
- RuntimeControlPort: exposes reload and provider setup/control operations without coupling core command semantics to a loader.

Minecraft, Discord, and Telegram are presentation/input adapters over those services.

DecisionService remains the canonical owner of request state transitions and vanilla whitelist mutations.

Adapters MUST NOT:

- mutate repository rows directly;
- mutate vanilla whitelist state directly;
- independently decide whether a request transition is legal;
- implement their own historical username resolution;
- invent provider-specific decision semantics;
- claim success before the application service returns the final result.

### M9-D003 — Vanilla whitelist remains authoritative

Approval adds the exact requested Minecraft profile to the vanilla whitelist.

Undoing an approved request removes that exact requested profile from the vanilla whitelist and reopens the workflow request.

Manual whitelist changes remain authoritative. Gatehouse MUST NOT fight an external/manual whitelist addition or removal except when the administrator explicitly invokes a Gatehouse operation that is defined to mutate the whitelist.

### M9-D004 — Offline identity remains explicitly unauthenticated

Every administrator request detail view and provider request card MUST make the offline-mode trust boundary visible.

Use the concept:

~~~text
Offline-mode identity — Minecraft has not authenticated ownership of this username.
~~~

Do not imply that username or offline UUID identifies a Microsoft/Mojang account owner.

### M9-D005 — No IP persistence

M9 MUST NOT add IP address persistence, IP reputation, IP audit logging, or an IP-address database column.

Global abuse protection in M9 is username/workflow/global-rate based.

## 3. Canonical command grammar

Every interface implements the following logical grammar.

### 3.1 General

~~~text
/gatehouse
/gatehouse help [topic]
~~~

Running /gatehouse with no arguments is identical to /gatehouse help.

### 3.2 Request browsing

~~~text
/gatehouse requests [pending|resolving|approved|denied|blocked|all] [page]
/gatehouse show <request-ref>
~~~

Default requests filter: pending.

Default page: 1.

Fixed page size: 10. It is not configurable in 1.2.0.

Pending results sort oldest first so the command acts as a work queue.

All other status filters and all sort newest updated request first unless a later explicit requirement in this file says otherwise.

### 3.3 Decisions

~~~text
/gatehouse approve <request-ref> [reason...]
/gatehouse deny <request-ref> [reason...]
/gatehouse block <request-ref> [reason...]
/gatehouse reopen <request-ref> [reason...]
/gatehouse undo <request-ref> [reason...]
/gatehouse unblock <username> [reason...]
~~~

Semantics are fixed:

- approve is valid only for PENDING;
- deny is valid only for PENDING;
- block is valid only for PENDING;
- reopen is valid only for DENIED or BLOCKED;
- undo is valid only for APPROVED;
- unblock removes the active identity block for the normalized username but does not rewrite the historical BLOCKED request.

Reopen of a BLOCKED request removes the corresponding identity block and changes that request to PENDING in one business operation.

Undo of an APPROVED request removes the exact requested profile from the vanilla whitelist and changes that request to PENDING using the existing crash-aware resolving flow.

Do not make undo a generic alias for reopen. The words have distinct meaning in 1.2.0.

Reasons are optional for all decisions.

### 3.4 Status and runtime management

~~~text
/gatehouse status
/gatehouse reload
~~~

### 3.5 Provider operations

~~~text
/gatehouse provider status [discord|telegram]
/gatehouse provider test <discord|telegram>
~~~

provider test sends one non-secret test message to the configured destination and returns the actual provider result. It MUST NOT create a workflow request.

### 3.6 Guided setup

~~~text
/gatehouse setup status
/gatehouse setup discord
/gatehouse setup telegram
/gatehouse setup bind <discord|telegram> <code>
/gatehouse setup cancel <discord|telegram>
~~~

The exact setup flow is defined in Section 13.

### 3.7 External administrator management

~~~text
/gatehouse admin list <discord|telegram>
/gatehouse admin add <discord|telegram> <principal> <view|decide|manage>
/gatehouse admin remove <discord|telegram> <principal>
~~~

Minecraft MANAGE sources may administer external principals.

Discord and Telegram MANAGE principals may administer principals for their own provider only.

No interface may create a Minecraft operator or change Minecraft permission levels.

## 4. Command behavior by interface

### 4.1 Minecraft

Minecraft registers only the root literal gatehouse.

The command tree MUST be identical on Fabric, Forge, and NeoForge.

The root command MUST remain registered when Gatehouse runtime is STARTING, DEGRADED, or otherwise unavailable.

The root Brigadier requires predicate may enforce Minecraft authorization but MUST NOT hide the tree based on Gatehouse runtime health.

The following commands remain usable during degraded runtime:

- /gatehouse
- /gatehouse help
- /gatehouse status
- /gatehouse reload
- /gatehouse setup status where sufficient configuration state is available

Commands that require unavailable business services return an actionable Gatehouse error instead of appearing nonexistent.

Minecraft must provide Brigadier suggestions for:

- status names;
- provider names;
- active request usernames for approve/deny/block;
- terminal request usernames for reopen/undo as applicable;
- request ID prefixes where practical.

Console and RCON are valid command sources.

Minecraft output must be plain enough for console/RCON and readable in chat. Do not require clickable text for correctness.

### 4.2 Discord

Discord registers exactly one application command named gatehouse.

All operations are subcommands or subcommand groups under /gatehouse.

Use native Discord typed options and autocomplete where supported.

Use ephemeral interaction responses for:

- help;
- errors;
- confirmations;
- setup;
- status;
- provider tests;
- admin management;
- detailed request inspection when invoked as a command.

The shared approval request card remains a channel/DM message and MUST NOT be overwritten with a private confirmation prompt.

Discord buttons are shortcuts to the same AdminCommandService/DecisionService operations and use the confirmation rules in Section 10.

### 4.3 Telegram

Telegram registers exactly one bot command through setMyCommands:

~~~text
/gatehouse — Gatehouse administration and whitelist requests
~~~

Do not register separate /approve, /status, /requests, or other textual bot commands.

The Telegram long poller MUST receive both:

- callback_query;
- message.

Text command parsing handles only messages beginning with /gatehouse, including the optional @BotUsername suffix Telegram may append in group chats.

Non-Gatehouse messages are ignored.

Inline keyboards are used for:

- request actions;
- request pagination;
- confirmation;
- setup where useful.

Every callback query MUST be acknowledged promptly with answerCallbackQuery before long-running work.

The final command or decision result MUST be surfaced to the invoking administrator. Do not fire-and-forget a DecisionService call.

## 5. Authorization model

Gatehouse 1.2.0 has exactly three administrator capabilities.

### VIEW

May execute:

- help;
- requests;
- show;
- status;
- provider status.

### DECIDE

Includes VIEW and may also execute:

- approve;
- deny;
- block;
- reopen;
- undo;
- unblock.

### MANAGE

Includes DECIDE and may also execute:

- reload;
- provider test;
- setup;
- admin list/add/remove.

### 5.1 Minecraft authorization

1.2.0 introduces:

~~~json
"minecraft": {
  "viewPermissionLevel": 2,
  "decisionPermissionLevel": 3,
  "managePermissionLevel": 4
}
~~~

Validation:

- each level is an integer from 0 through 4;
- viewPermissionLevel <= decisionPermissionLevel <= managePermissionLevel.

Backward compatibility for 1.1.x config:

If minecraft permission fields are absent and requests.commandPermissionLevel exists, normalize in memory as:

- decision = old commandPermissionLevel;
- view = max(0, decision - 1);
- manage = min(4, decision + 1).

The default generated 1.2.0 config MUST use the new minecraft block and MUST NOT generate requests.commandPermissionLevel.

The legacy field remains readable for the 1.2.x line but is documented as deprecated.

### 5.2 Discord authorization

1.2.0 canonical Discord authorization configuration is:

~~~json
"principals": [
  { "kind": "USER", "id": "123456789012345678", "access": "MANAGE" },
  { "kind": "ROLE", "id": "234567890123456789", "access": "DECIDE" }
]
~~~

Allowed values:

- kind: USER or ROLE;
- access: VIEW, DECIDE, MANAGE.

Stable IDs authorize. Display names never authorize.

Backward compatibility:

- existing allowedUserIds normalize as USER + DECIDE;
- existing allowedRoleIds normalize as ROLE + DECIDE.

If canonical principals are present, they are authoritative. Do not merge legacy allowlists into a non-empty canonical principals list.

When Gatehouse rewrites provider configuration through guided setup/admin management, it writes canonical principals and removes legacy allowlist keys for that provider.

### 5.3 Telegram authorization

Canonical Telegram authorization configuration is:

~~~json
"principals": [
  { "userId": "123456789", "access": "MANAGE" }
]
~~~

Allowed access values are VIEW, DECIDE, MANAGE.

Backward compatibility:

- existing allowedUserIds normalize as DECIDE.

If canonical principals are present, they are authoritative.

### 5.4 Authorization failures

An unauthorized actor causes zero business mutation.

The response must identify the missing Gatehouse capability without leaking secrets.

Examples:

~~~text
This Gatehouse action requires DECIDE access.
This Gatehouse action requires MANAGE access.
~~~

Do not expose raw configuration contents to unauthorized actors.

## 6. Request state and action policy

RequestActionPolicy is the single source of action availability.

### PENDING

Enabled:

- approve;
- deny;
- block.

Disabled:

- reopen;
- undo.

### RESOLVING

No mutating request action is enabled.

The UI indicates that another operation is in progress.

### APPROVED

Enabled:

- undo.

Visible label in graphical providers:

~~~text
Undo approval
~~~

### DENIED

Enabled:

- reopen.

Visible label:

~~~text
Reopen
~~~

### BLOCKED

Enabled:

- reopen.

Visible label:

~~~text
Unblock & reopen
~~~

No provider adapter may derive its own button state from a generic terminal boolean.

## 7. Request reference resolution

RequestResolver implements all reference resolution.

### 7.1 Accepted request-ref forms

1. full canonical UUID;
2. UUID prefix of at least 8 canonical UUID characters;
3. exact username, normalized with Locale.ROOT for lookup.

A UUID prefix is valid only if it matches exactly one request. Ambiguous prefixes fail and require more characters or a full UUID.

Never silently pick one of multiple prefix matches.

### 7.2 Resolution by command

show:

- full UUID/prefix selects that exact request;
- username selects the most recently created request for that normalized username, regardless of status.

approve, deny, block:

- full UUID/prefix must resolve to a PENDING request;
- username resolves only the active request for that normalized username;
- if no active request exists, return current/latest state and the valid next action when possible.

reopen:

- full UUID/prefix must select DENIED or BLOCKED;
- username selects the most recent DENIED or BLOCKED request only when there is no active PENDING/RESOLVING request for that username;
- if an active request exists, fail with an active-request conflict and show its reference.

undo:

- full UUID/prefix must select APPROVED;
- username selects the most recent APPROVED request only when there is no active PENDING/RESOLVING request for that username;
- if an active request exists, fail with an active-request conflict and show its reference.

### 7.3 Active conflict rule

A terminal request MUST NOT be reopened while another request for the same normalized username is PENDING or RESOLVING.

This conflict is detected explicitly before the repository attempts the update.

Do not use a SQLite unique-index exception as normal control flow.

Example:

~~~text
Cannot reopen 88e56047 for ZIFT1: active request a672b419 already exists.
Resolve the active request first.
~~~

## 8. Decision correctness requirements

### 8.1 Preserve repository outcomes

DecisionService undo/reopen logic MUST preserve the actual repository result.

It MUST NOT return UNDONE/REOPENED when repository mutation failed, conflicted, or returned another outcome.

### 8.2 Idempotent, state-aware feedback

Repeated/stale actions return descriptive current-state results.

Do not return only "already resolved".

Examples:

~~~text
ZIFT1 is already APPROVED.
Approved by Vlad via Discord at 2026-09-18T14:32:00Z.
~~~

~~~text
Cannot deny ZIFT1 because request 88e56047 is APPROVED.
Use /gatehouse undo ZIFT1 to remove the approval and reopen it.
~~~

~~~text
Cannot approve ZIFT1 because request 88e56047 is DENIED.
Use /gatehouse reopen ZIFT1 first.
~~~

### 8.3 Resolution metadata

show and terminal provider cards display, where present:

- exact player name;
- request ID;
- status;
- first attempt time;
- last attempt time;
- attempt count;
- resolved time;
- resolver display name;
- resolver provider;
- reason.

Stable external actor IDs remain audit data but need not be displayed publicly.

## 9. Request list UX

/gatehouse requests defaults to PENDING.

Output includes:

- selected status/filter;
- page X/Y;
- total matching count;
- for each row: exact username, age/wait time, attempt count, short request reference;
- a usage hint for show.

For PENDING, oldest requests are listed first.

Derived stale marker:

A PENDING request older than requests.pendingStaleAfterHours is displayed as STALE.

STALE is NOT a RequestStatus and MUST NOT create a persistence state transition in 1.2.0.

Default stale threshold: 168 hours.

Example:

~~~text
Gatehouse requests — PENDING — page 1/2 — 14 total

1. ZIFT1      18m waiting   6 attempts   88e56047
2. Alice      11m waiting   1 attempt    a672b419
3. Steve      9d waiting    3 attempts   09ad83bc   STALE

/gatehouse show <player|request>
~~~

Invalid filters and invalid page numbers are errors. Invalid status MUST NOT silently mean "all".

## 10. Confirmation and stale-interaction safety

### 10.1 Minecraft

Minecraft chat, console, and RCON commands do not use interactive confirmation.

The explicit typed command is the confirmation.

### 10.2 Discord and Telegram

Graphical mutating actions use confirmation.

Confirmation is required for:

- approve;
- deny;
- block;
- reopen;
- undo.

unblock invoked as a textual command does not require a second confirmation.

### 10.3 ConfirmationStore

Implement a provider-neutral ConfirmationStore.

A confirmation record contains:

- opaque random token;
- provider;
- initiating stable actor ID;
- request ID;
- requested action;
- expected request status;
- creation time;
- expiration time.

TTL is fixed at 60 seconds in 1.2.0.

The provider callback carries the opaque token, not trusted business data.

On confirm:

1. validate token exists;
2. validate not expired;
3. validate provider matches;
4. validate actor matches;
5. re-fetch current request;
6. validate current status still matches expected status;
7. consume the token exactly once;
8. execute through AdminCommandService/DecisionService.

Expired, replayed, wrong-actor, missing, or stale confirmations perform zero mutation.

Cancel consumes the token and reloads current request state.

### 10.4 Presentation

Discord confirmation is ephemeral. It MUST NOT replace the shared request card.

Telegram may edit the requesting message/keyboard for confirmation, but cancel/expiry must restore the current request presentation, not stale cached state.

## 11. Player reconnect abuse protection

The login path remains non-blocking with respect to SQLite and providers.

### 11.1 Admission coalescing

AdmissionWorker MUST coalesce repeat attempts by normalized username.

At most one queued work item per normalized username may exist at a time.

Repeated attempts while work is queued or processing increment an in-memory batch counter and update the latest attempt time rather than adding another queue entry.

After the worker drains completely, persistent attemptCount must reflect all successfully accepted attempts during normal runtime. Tests may wait for the asynchronous drain before asserting the count.

A crash may lose only the not-yet-persisted attempt telemetry window. It must not create contradictory request state.

### 11.2 Known-state fast path

If admission cache says:

- PENDING: return pending response; do not create a second independent persistence queue item unless a coalesced telemetry batch is required;
- DENIED: return cooldown response;
- BLOCKED: return blocked response;
- DEGRADED: return unavailable response.

Business state does not require a database read on the login thread.

### 11.3 Global new-request limiter

Apply a global token bucket only to unknown normalized usernames that would represent candidate new requests.

Defaults:

- refill rate: 30 new-request candidates per minute;
- burst capacity: 10.

Known PENDING, DENIED, or BLOCKED identities are not rejected by this limiter; they receive their correct existing-state response.

When rate limited, do not enqueue a candidate new request.

Use a non-persistent admission result such as THROTTLED.

Player response:

~~~text
Gatehouse is receiving too many new whitelist requests.
Please try again shortly or contact a server administrator.
~~~

### 11.4 Maximum pending circuit breaker

Default maximum active PENDING + RESOLVING requests: 500.

The runtime maintains an in-memory active count hydrated at startup and updated after request transitions.

If the count is at the configured maximum, unknown usernames do not enqueue new requests.

Existing requests continue to work.

### 11.5 Config defaults

The 1.2.0 generated requests configuration is:

~~~json
"requests": {
  "denialCooldownMinutes": 1440,
  "queueCapacity": 2000,
  "attemptCoalesceSeconds": 5,
  "providerRefreshSeconds": 30,
  "newRequestRatePerMinute": 30,
  "newRequestBurst": 10,
  "maxPendingRequests": 500,
  "pendingStaleAfterHours": 168,
  "supportMessage": ""
}
~~~

Validation:

- denialCooldownMinutes >= 0;
- queueCapacity >= 1;
- attemptCoalesceSeconds from 1 through 60;
- providerRefreshSeconds from 1 through 3600;
- newRequestRatePerMinute >= 1;
- newRequestBurst >= 1;
- maxPendingRequests >= 1;
- pendingStaleAfterHours >= 1;
- supportMessage maximum 300 characters.

No implementation agent may invent different defaults without changing this document first.

## 12. Outbox and provider spam resistance

### 12.1 Event classes

REQUEST_CREATED:

- never coalesced away;
- required to establish publication.

Terminal business transition:

- never delayed by providerRefreshSeconds;
- creates an immediate terminal update event.

Attempt-only update:

- coalescible;
- not required to preserve every intermediate attempt count in provider history.

### 12.2 READY update coalescing

For one request, there may be at most one READY attempt-only REQUEST_UPDATED event.

If a REQUEST_UPDATED event is PROCESSING and another attempt-only refresh becomes necessary, one READY follow-up may exist.

Do not create N READY events for N reconnects.

### 12.3 Terminal supersession

Before inserting the terminal provider update for a request, obsolete READY attempt-only update events for the same request are completed/superseded.

The terminal update renders the latest request state.

### 12.4 Provider refresh cadence

Attempt-only provider updates occur no more often than requests.providerRefreshSeconds.

Terminal transitions bypass this delay.

Provider publications must converge to current state after outage recovery; they do not replay every obsolete attempt counter intermediate state.

## 13. Guided BYOB provider setup

Hosted/multi-tenant Gatehouse bots remain out of scope. M9 improves bring-your-own-bot setup only.

Provider tokens are still operator-supplied secrets and are never entered through Discord or Telegram chat.

### 13.1 Provider setup states

Provider operational state supports:

- DISABLED;
- SETUP_REQUIRED;
- STARTING;
- HEALTHY;
- DEGRADED;
- UNAVAILABLE;
- STOPPED.

Definitions:

DISABLED:
- explicitly enabled=false.

SETUP_REQUIRED:
- enabled=true but required non-secret binding/admin configuration is incomplete, or token is missing and the operator must supply it.

STARTING:
- connection/validation currently starting.

HEALTHY:
- provider can perform its required operations.

DEGRADED:
- provider is connected/partially available but an expected operation is failing.

UNAVAILABLE:
- provider cannot currently be used.

STOPPED:
- lifecycle is intentionally stopped during shutdown/reload.

### 13.2 Setup prerequisite

The bot token must already exist in config/environment before a remote bind can succeed.

If token is absent, setup status gives an actionable message telling the operator to configure the environment/config token and reload.

Never echo the token.

### 13.3 Setup initiation

A Minecraft MANAGE source runs:

~~~text
/gatehouse setup discord
~~~

or:

~~~text
/gatehouse setup telegram
~~~

Gatehouse creates a one-time setup session.

Session properties:

- random 8-character Crockford Base32 code;
- omit visually ambiguous characters;
- valid for 10 minutes;
- single use;
- provider scoped;
- persisted hashed, never stored as plaintext;
- survives server restart until expiry/cancellation;
- audit creation and consumption.

Suggested persistence is a provider_setup_sessions table. If another persistence representation is used, it must preserve the exact behavioral contract and remain internal.

### 13.4 Remote binding

In the target provider context, a user runs:

~~~text
/gatehouse setup bind discord <code>
~~~

or:

~~~text
/gatehouse setup bind telegram <code>
~~~

Binding captures:

Discord guild channel:
- guild ID;
- channel ID;
- invoking Discord user ID as initial MANAGE principal.

Discord DM:
- dmUserId;
- invoking Discord user ID as initial MANAGE principal;
- guildId and channelId remain blank where not applicable.

Telegram:
- current chat ID;
- invoking Telegram user ID as initial MANAGE principal.

After capture:

1. validate provider reachability/permissions;
2. write only non-secret binding/principal config;
3. preserve the original token field exactly, including an environment placeholder;
4. reload provider configuration;
5. send a test message;
6. report final success/failure;
7. consume setup code only after binding validation succeeds, except a code rejected for security reasons may also be invalidated.

### 13.5 Config writing

Introduce a safe ConfigWriter for M9.

ConfigWriter MUST:

- parse and preserve the raw token string;
- never write expanded secret values;
- update only intended provider/non-secret fields;
- write atomically using temporary file + replace;
- preserve unrelated configuration fields;
- normalize legacy authorization fields to canonical principals when that provider is written.

### 13.6 Setup resume/status

/gatehouse setup status reports each provider as a checklist.

Example:

~~~text
Discord setup
✓ Bot token configured
✓ Bot connected
✓ Guild identified: My Server
✗ Approval channel not selected
✗ Initial Gatehouse administrator not confirmed

Next: run /gatehouse setup discord in Minecraft to generate a binding code.
~~~

If an unexpired setup session exists, show that a session exists and its expiry time. Do not redisplay the secret setup code after its creation response.

### 13.7 Cancellation

/gatehouse setup cancel <provider> invalidates all unexpired setup sessions for that provider.

## 14. Provider cards and graphical UX

### 14.1 Pending card priority

Pending provider cards prioritize operational information.

Required fields:

- title;
- exact player;
- PENDING status;
- waiting/age;
- attempt count;
- last attempt;
- offline identity warning;
- request reference.

Offline UUID moves to detailed show output and does not need prominent placement on the compact card.

Example logical content:

~~~text
Whitelist request — PENDING

Player: ZIFT1
Waiting: 18 minutes
Attempts: 6
Last attempt: 42 seconds ago

Offline-mode identity — Minecraft has not authenticated ownership of this username.

Request: 88e56047
~~~

### 14.2 Terminal card

Required:

- exact player;
- terminal state;
- resolver display name;
- resolver provider;
- resolved time;
- reason when present;
- appropriate recovery action.

Example:

~~~text
Whitelist request — DENIED

Player: ZIFT1
Resolved by: Vlad · Discord
Resolved: 2 minutes ago
Reason: Application information did not match

[ Reopen ]
~~~

### 14.3 Request reference display

Compact cards/lists may display the first 8 characters of the UUID because RequestResolver supports unique prefixes of at least 8 characters.

Full UUID remains available in /gatehouse show.

Never display an identifier as the primary operational reference if the command resolver cannot accept it.

### 14.4 Reason capture

Minecraft: trailing reason text.

Discord:
- Approve may confirm directly;
- Deny and Block confirmation UI must provide an Add reason path;
- Reopen and Undo may accept an optional reason.

Telegram:
- equivalent behavior may use a follow-up prompt/message;
- timeout/cancel must not mutate request state.

Reasons must never be required for a normal decision.

Maximum reason length: 500 characters after trimming.

Blank reason becomes absent/null.

## 15. Player-facing messages

Player messages must be actionable and must not encourage reconnect spam.

### 15.1 First accepted request attempt

~~~text
Whitelist request submitted for <player>.
An administrator must approve it before you can join.
Try again after approval.
~~~

Do not claim durable creation if admission is already known degraded or the request was rejected by abuse controls.

### 15.2 Pending

~~~text
Your whitelist request for <player> is still pending.
You do not need to create another request.
Try again after an administrator approves it.
~~~

If the in-memory admission state already contains a persisted request ID, append:

~~~text
Reference: <8-char-prefix>
~~~

Do not perform a login-thread database read just to obtain the reference.

### 15.3 Denied cooldown

Show remaining cooldown, rounded up to a human-readable whole minute/hour as appropriate.

Example:


## 17. Safe reload

Reload is a recovery feature and must work from degraded state.

### 17.1 Command result

/gatehouse reload returns final outcome, not only "reload started".

Possible high-level outcomes:

- SUCCESS;
- FAILED_ROLLED_BACK;
- FAILED_DEGRADED;
- RESTART_REQUIRED.

### 17.2 Sequence for healthy runtime

1. read candidate config;
2. parse and validate without mutating live runtime;
3. preserve raw secret placeholders;
4. compare structural settings;
5. if database.path changes, return RESTART_REQUIRED and keep old runtime untouched;
6. snapshot old validated config;
7. enter RELOADING;
8. stop old runtime cleanly;
9. start candidate runtime;
10. if candidate succeeds, commit it as active and report SUCCESS;
11. if candidate fails, start a fresh runtime from old validated config;
12. if rollback succeeds, report FAILED_ROLLED_BACK with candidate failure reason;
13. if rollback fails, install degraded runtime and report FAILED_DEGRADED with both failures.

Do not run two live Discord/Telegram provider sessions concurrently as part of reload.

### 17.3 Sequence for degraded runtime

If no healthy live database/runtime owns the current structural resource, corrected database.path may be accepted during recovery reload.

The implementation must validate that no healthy runtime is being abandoned before allowing a structural path change.

### 17.4 Error preservation

Reload failure messages and logs must redact tokens and secrets.

## 18. External command rate limiting

Discord and Telegram commands are rate-limited per stable external actor.

Fixed 1.2.0 defaults:

Read operations:
- 5 per second;
- burst 10.

Mutating operations:
- 2 per second;
- burst 4.

Minecraft commands are not subject to this external actor limiter.

Rate-limit rejection performs zero business mutation and returns a short retry-after indication.

Provider callback retries for the same consumed confirmation token are treated as replay, not as a second decision.

Business idempotency and concurrency controls remain mandatory even with rate limiting.
